[지난 편](/blog/2026/01/09/ai-agent-pipeline-8-rollback-mechanism/)에서는 재시도와 롤백 메커니즘을 다뤘습니다.

이번 편에서는 **파이프라인을 운영하면서 발견한 개선점들**을 정리했습니다.

<!--more-->

8편까지의 파이프라인으로 약 250개의 학습 콘텐츠를 생성했습니다. 하지만 블로그 시리즈를 작성하면서 실제 콘텐츠 생성은 거의 하지 않았습니다. 이유는 토큰 비용이었습니다. 한 번에 많은 양을 생성하면 비용을 아낄 수 있기 때문에, 시리즈 작성에 집중하면서 생성은 미뤄뒀습니다.

대신 그 시간에 설계 문서와 프로세스를 다시 점검했습니다. 시리즈를 쓰려면 파이프라인의 흐름을 설명해야 하고, 설명하려면 각 단계가 왜 그렇게 설계되었는지 이해해야 했습니다. 그 과정에서 몇 가지 개선점을 발견했습니다.

## 1. category-parser 추가

[2편](/blog/2025/12/16/ai-agent-pipeline-2-what-to-generate/)에서 메타데이터 파이프라인을 소개했습니다. metadata-parser와 metadata-generator로 토픽 문서에서 category.yaml과 빈 마크다운 파일을 생성하는 구조였습니다.

그런데 한 가지 문제가 있었습니다. 카테고리 목록이 스크립트에 하드코딩되어 있었습니다.

```bash
# 기존 방식: 카테고리 목록이 스크립트에 하드코딩
get_topics() {
    local subject=$1
    case "$subject" in
        "javascript-core-concepts")
            echo "01-variables 02-type-system 03-operators ... 10-functions-basic"
            ;;
        ...
    esac
}
```

각 주제당 약 10개 카테고리만 정의되어 있었습니다. 토픽 문서에는 javascript-core-concepts만 해도 42개 카테고리가 있는데, 스크립트에는 10개뿐이었습니다. 나머지 32개를 추가하려면 스크립트를 직접 수정해야 했습니다. 10개 주제의 총 169개 카테고리를 모두 스크립트에 하드코딩하는 건 비현실적이었습니다.

해결책은 토픽 문서에서 카테고리 목록을 자동으로 추출하는 것이었습니다. 토픽 문서를 보면 `### 1. 변수 완전 정복`, `### 2. JavaScript 타입 시스템` 같은 패턴이 있습니다. 이 패턴을 파싱하면 모든 카테고리를 추출할 수 있습니다.

그래서 category-parser 에이전트를 추가했습니다. 토픽 문서를 읽어서 `### N. 제목` 패턴을 찾고, 각 카테고리에 ID를 부여한 뒤 manifest 파일로 저장합니다.

```json
{
  "categories": {
    "javascript-core-concepts": ["01-variables", "02-type-system", ..., "42-metaprogramming"]
  }
}
```

이제 스크립트는 하드코딩된 목록 대신 manifest 파일에서 카테고리를 읽어옵니다. 토픽 문서에 카테고리가 추가되면 category-parser를 실행하기만 하면 됩니다. 스크립트를 수정할 필요가 없습니다.

category-parser는 새 ID를 생성하기 전에 기존 ID가 있는지 먼저 확인합니다. manifest 파일에 해당 카테고리가 있으면 그 ID를 사용합니다. manifest에 없더라도 디렉토리가 이미 존재하면 그 디렉토리 이름을 ID로 사용합니다. 둘 다 없을 때만 새 ID를 생성합니다.

이렇게 하면 기존 10개 카테고리의 파일 경로는 유지되면서, 새로 추가된 32개 카테고리만 새 ID를 받습니다.

## 2. IMPROVEMENT_NEEDED 제거

8편에서 롤백 메커니즘을 설명하면서 코드를 다시 살펴봤습니다. 그러다 content-validator의 프롬프트에 `IMPROVEMENT_NEEDED`라는 필드를 다루는 규칙이 있는 것을 발견했습니다.

검증 점수가 90점 미만이면 어떤 에이전트가 개선해야 하는지 파일에 기록하고, 해당 에이전트부터 다시 시작하는 방식이었습니다. 4편에서 언급한 초기 접근 방식의 흔적이었습니다.

하지만 8편에서 롤백/재시도 로직을 보강하면서 이 방식은 의미가 없어졌습니다. 이제 검증 실패 시 오케스트레이션 스크립트가 백업에서 복구하고 해당 에이전트를 재시도합니다. 에이전트가 직접 다음 에이전트를 지정할 필요가 없습니다.

```markdown
# 변경 전
- VALIDATION_SCORE < 90: 개선 지시 (IMPROVEMENT_NEEDED, CURRENT_AGENT 재설정)

# 변경 후
- VALIDATION_SCORE < 90: 파이프라인 실패 (STATUS: FAILED)
- 재시도 위임: 오케스트레이션이 백업/복구로 재시도
```

에이전트는 실패만 알리면 됩니다. 재시도 결정은 오케스트레이션이 합니다.

## 3. practice-writer 제거

파이프라인이 완성되고 나서 개발 외 다른 주제로 테스트해봤습니다. 역사, 언어, 수학 같은 비-프로그래밍 분야에도 적용할 수 있는지 확인하고 싶었습니다.

결과적으로 문서는 잘 작성되었습니다. 파싱도 정상이었고, 앱에서 렌더링도 문제없었습니다. 하지만 콘텐츠를 살펴보니 practice-writer가 생성하는 `Code Patterns`와 `Experiments` 섹션이 어색했습니다.

프로그래밍 주제에서는 코드 실습이 자연스럽습니다. 하지만 역사나 언어 학습에서 코드 블록이 필요할까요? 그리고 애초에 이 앱은 모바일 환경입니다. 코드 에디터도 없고, 실행 환경도 없습니다. 코드 실습 섹션이 있어도 실제로 실습할 방법이 없었습니다.

practice-writer를 제거했습니다.

---

## 4. content-initiator 제거

사실 content-initiator가 실행되지 않는다는 건 이전부터 알고 있었습니다. 메타데이터 파이프라인에서 이미 마크다운 파일을 생성하고 있었기 때문에, 콘텐츠 파이프라인의 1단계인 content-initiator는 전제조건 검사에서 "이미 파일이 존재함"으로 판단되어 건너뛰어지고 있었습니다. 당시에는 어차피 결과가 같으니 크게 신경 쓰지 않았습니다.

2, 3번 개선 작업을 진행하면서 이 부분을 다시 들여다보게 되었습니다. content-initiator의 역할은 단순했습니다. 빈 마크다운 파일을 생성하고 기본 front matter를 작성하는 것. 이 정도라면 에이전트가 아니라 쉘 함수로 충분했습니다.

단순히 에이전트를 삭제하는 것으로 끝나지 않았습니다. `initialize_markdown_file()` 함수를 추가하여 파일 초기화 로직을 쉘에서 직접 처리하도록 변경했습니다. 그리고 이 함수를 검증 실패 시 롤백 로직과 연결했습니다. 메타데이터 파이프라인에서 생성된 파일이 콘텐츠 생성 중 손상될 수 있기 때문에, 롤백 시 파일을 깨끗한 상태로 재초기화하는 기능이 필요했습니다.

결과적으로 7개였던 콘텐츠 에이전트가 5개로 줄었습니다. practice-writer와 content-initiator가 제거되면서 파이프라인이 한결 가벼워졌습니다.

---

## 5. JSON Schema로 로그 구조화

IMPROVEMENT_NEEDED를 제거하면서 새로운 문제가 생겼습니다. 기존에는 검증 실패 시 content-validator가 직접 문제 에이전트를 지정해서 핸드오프 로그에 남겼습니다. 하지만 이제 그 로직이 사라졌기 때문에, 롤백 후 재시도할 때 어떤 에이전트가 문제였는지 알 수 없었습니다.

LLM 출력에서 에이전트별로 자주 사용되는 패턴을 grep해서 문제 에이전트를 찾아야 했습니다. 이 방식은 불안정했습니다. Claude에게 물어보니 JSON 스키마를 사용하면 출력 형식을 고정할 수 있다고 제안했습니다.

```bash
# v8: JSON 스키마로 구조화된 출력
"$CLAUDE_PATH" -p "$prompt" \
    --output-format json \
    --json-schema "$json_schema" \
    ...

# jq로 간단하게 추출
local value=$(jq -r ".structured_output.$field // empty" "$json_file" 2>/dev/null)
```

각 에이전트가 출력해야 하는 필드를 JSON 스키마로 정의하고, Claude가 해당 스키마에 맞춰 구조화된 JSON을 반환하도록 했습니다. 검증 실패 시 어떤 에이전트가 문제인지, 어떤 항목이 미달인지 JSON에서 바로 확인할 수 있게 되었습니다.

## 마무리

이번 편에서는 파이프라인을 운영하면서 발견한 개선점들을 정리했습니다.

- **category-parser 추가**: 하드코딩된 169개 카테고리 목록 대신 docs/topic에서 동적으로 파싱
- **IMPROVEMENT_NEEDED 제거**: 에이전트 간 개선 루프를 걷어내고 오케스트레이션의 롤백/재시도로 단순화
- **practice-writer 제거**: 개발 외 다른 주제로 테스트한 결과 불필요하다고 판단
- **content-initiator 제거**: 메타데이터 파이프라인과 중복되는 작업을 쉘 함수로 대체
- **JSON Schema 적용**: 에이전트 출력을 구조화하여 로그 파싱 안정화

7개였던 콘텐츠 에이전트가 5개로 줄었고, 에이전트의 역할이 더 명확해졌습니다. 복잡한 개선 루프 대신 단순한 실패/재시도 구조가 되면서 디버깅도 쉬워졌습니다.

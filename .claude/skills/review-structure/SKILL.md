# 블로그 구조 검토

이 문서는 구조 검토 기준의 단일 진실이다. 에이전트 어댑터는 이 기준을 그대로 사용한다.

## 입력과 역할

- 대상 초안의 명시적 경로, 사용자 작성 의도, 근거 자료를 읽는다. 자동 작성 흐름에서는 최근 수정 파일을 추측하지 않는다.
- 단독 호출에서 경로가 없으면 후보를 조회해 대상을 확정한다. 여러 후보 중 임의로 하나를 검토하지 않는다.
- `content/pages/about.md`, `.claude/rules/blog-tone.md`, `.claude/rules/blog-content-criteria.md`를 함께 읽는다.
- 작성자와 다른 검토자가 수행한다. 검토자는 초안을 수정하지 않는다.

## 검토 기준

1. **의도**: 소개에 적힌 실제 경험, 시행착오, 선택 이유를 기록하는 목적에 맞는가. 경험기를 제품 순위표나 일반 기술 해설로 바꾸지 않았는가. 작성 요청의 제외 사항도 지켰는가.
2. **시간 순서**: 당시 상황 → 시도 → 관찰 → 다음 선택이 연결되는가. 회상 시점과 현재 판단을 구분했는가. 불확실한 기억을 임의 날짜로 고정하지 않았는가.
3. **주장과 근거**: 직접 경험, 주관적 인상, 확인 가능한 외부 사실을 구분했는가. 체감 사용량이나 작업 지속 시간을 모든 사용자에게 적용되는 성능·정책으로 일반화하지 않았는가. 외부 사실의 출처가 해당 기간과 제품·플랜을 실제로 뒷받침하는가.
4. **불확실성**: 확인되지 않은 모델명·출시일·요금·제한 변경을 단정하지 않았는가. 현재 정책만으로 과거 정책 변경을 입증하지 않았는가. 기록이 없다는 이유로 경험 자체를 부정하지 않았는가.
5. **구조**: 제목과 도입이 실제 내용을 안내하고, 각 선택의 이유와 결과가 연결되는가. 실패한 시도를 성공담으로 포장하지 않았는가. 결말이 저자의 현재 판단에서 자연스럽게 끝나는가.
6. **메타데이터와 맥락**: 날짜·언어·카테고리·시리즈 연결이 맞는가. 미발행 글을 이미 공개된 이전 글처럼 참조하지 않았는가. 단독 경험기에 시리즈나 다음 편 예고를 강제하지 않는다.
7. **깊이**: 글의 종류에 맞는 구체적인 상황과 선택 근거가 있는가. 기술 해설에 적용하는 5요소를 경험기의 필수 형식으로 강제하지 않는다. 기술 설명·코드·독자 참여 질문을 채우기 위해 추가하지 않는다.

## 결과와 수정 흐름

각 문제는 위치, 위 기준에 따른 이유, 의미를 보존하는 수정 방향으로 보고한다. 저자만 아는 경험이나 의미 변경이 필요한 경우에만 확인 사항으로 구분한다. 모든 단계의 형식적 확인이나 옵션 선택을 요구하지 않는다.

단독 검토 요청은 제안으로 끝낸다. 사용자가 초안 작성·수정까지 맡긴 흐름에서는 작성자가 그 권한 안에서 수정안을 적용한다. 검토자가 스스로 고치고 통과시키지 않는다. 기존 권한으로 해결할 수 있는 수정마다 재승인을 받지 않는다.

## 자동 작성 흐름의 검토 기록

`.claude/skills/write-post/SKILL.md`의 JSON 보고서 계약과 `python3 script/blog-review.py --help`를 따른다. 상태 파일 경로를 입력받아 `status --state <경로>`로 대상과 현재 해시를 확인한다. 읽은 초안과 근거가 그 스냅샷에 해당하는지 확인하고 구조 보고서를 작성한다.

보고서의 `stage`는 `structure`다. 현재 `draft_sha256`와 `policy_sha256`, 작성자와 구분되는 `reviewer`, 판정과 모든 발견 사항을 기록한다. 발견 사항을 숨기거나 남겨 둔 채 `pass`로 표시하지 않는다. 정규화한 JSON은 `.local/blog/<slug>/`에 두고 `record --state <경로> --report <보고서>`로 등록한다.

구조 검토가 통과한 동일 스냅샷에만 별도 검토자가 문장 검토를 수행한다. 초안·근거·정책이 바뀌면 두 검토 모두 무효이며 구조 검토부터 다시 수행한다. 등록 실패나 오래된 보고서를 완료 근거로 사용하지 않는다.

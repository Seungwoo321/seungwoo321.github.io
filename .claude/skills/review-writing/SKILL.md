# 블로그 문장 검토

이 문서는 문장 검토 기준의 단일 진실이다. 에이전트 어댑터는 이 기준을 그대로 사용한다.

## 입력과 역할

- 대상 초안의 명시적 경로, 작성 의도, 근거 자료와 동일 스냅샷의 구조 검토 결과를 읽는다.
- `content/pages/about.md`, `.claude/rules/blog-tone.md`, `.claude/rules/blog-content-criteria.md`를 참조한다.
- 작성자 및 구조 검토자와 다른 검토자가 수행한다. 검토자는 초안을 수정하지 않는다.
- 단독 호출에서 대상이 없으면 후보를 조회해 확정한다. 자동 작성 흐름에서는 최근 수정 파일을 임의로 선택하지 않는다.

## 검토 기준

1. **의미와 확신 정도**: “느꼈다”, “기억한다”, “내 환경에서는”을 삭제해 일반 사실로 바꾸지 않는다. “약”, “정도” 같은 불확실성도 보존한다. 반대로 근거로 확인된 사실을 모호한 인상으로 낮추지 않는다.
2. **주체**: 사람이 직접 한 일과 도구가 수행한 일을 구분한다. 문장을 능동태로 고친다는 이유로 도구의 구현을 저자의 직접 구현으로 바꾸지 않는다.
3. **담백한 경험 서술**: 과장, 자기 홍보, 근거 없는 인과관계나 경쟁 제품에 대한 단정을 찾는다. 개인의 판단을 모든 독자에게 권하는 정답으로 바꾸지 않는다.
4. **문장과 연결**: 한 문장에 여러 생각이 겹치면 의미 단위로 나눈다. 문장 간 원인·결과·시간 연결과 지시어의 대상을 확인한다. 짧게 끊기만 해서 흐름을 해치지 않는다.
5. **독자 맥락**: 필요한 용어를 이해할 만큼 설명하되 경험기를 용어 사전이나 튜토리얼로 바꾸지 않는다. 도구·모델·플랜의 이름이 혼동되지 않는지 확인한다.
6. **표기와 근거**: 숫자·날짜·가격·이름은 근거 자료와 대조한다. 확인되지 않은 표기를 익숙한 제품명으로 추측 교정하지 않는다. 출처의 적용 범위가 문장 표현에서 확대되지 않았는지 확인한다.
7. **톤과 결말**: 자연스러운 서술형 산문체와 일관된 말투를 유지한다. `blog-tone.md`에 따라 조사 과정을 본문에 끼운 문장, 과도한 회상 표현과 반복 단서, 같은 결론의 재설명을 찾는다. 정형적인 요약·권유·독자 참여 질문을 강제하지 않는다.

## 결과와 수정 흐름

문제마다 위치, 원문, 제안, 이유를 적는다. 발견 사항은 모두 기록하며 개수 제한 때문에 누락하지 않는다. 표현 취향은 결함으로 만들지 않는다. 저자만 확인할 수 있는 경험이나 의미를 바꾸는 선택은 별도 확인 사항으로 남긴다.

단독 검토에서는 제안만 반환한다. 초안 작성·수정까지 위임된 흐름에서는 작성자가 의미를 보존하는 수정안을 적용할 수 있으며 항목마다 사용자 승인을 다시 요구하지 않는다. 검토자는 수정 적용과 통과 판정을 동시에 맡지 않는다.

구조나 사실 근거의 문제가 발견되면 문장 수준에서 덮지 않는다. 해당 문제를 보고하고 작성자의 수정 후 구조 검토부터 다시 수행한다.

## 자동 작성 흐름의 검토 기록

`.claude/skills/write-post/SKILL.md`의 JSON 보고서 계약과 `python3 script/blog-review.py --help`를 따른다. `status --state <경로>`로 대상·현재 해시·구조 검토 통과를 확인한다. 같은 스냅샷에 대한 구조 통과가 없으면 문장 검토를 통과 처리하지 않는다.

보고서의 `stage`는 `writing`이다. 현재 `draft_sha256`와 `policy_sha256`, 작성자·구조 검토자와 구분되는 `reviewer`, 판정과 모든 발견 사항을 기록한다. `pass`는 발견 사항이 없는 경우에만 사용한다. 정규화한 JSON은 `.local/blog/<slug>/`에 두고 `record --state <경로> --report <보고서>`로 등록한다.

초안·근거·정책 변경은 두 검토를 모두 무효화한다. 수정 후 구조 → 문장 순서로 다시 검토한다. 마지막 `check --state <경로>` 성공은 이 두 검토의 완료를 뜻하며 발행 권한을 뜻하지 않는다.
